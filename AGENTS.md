# AGENTS.md

Working brief for an AI coding agent, not documentation for people (the README covers that): the rules, invariants and gotchas needed to change this project correctly without rediscovering them.

## Hard rules
- **Never shadow a real git command** - passthrough is the whole premise, so an enhanced view always gets a distinct verb (`trace`, not `log`; the `i` prefix for interactive: `irepos`/`ilog`/`ibranch`/`itag`/`istatus`/`iscan`).
- Scratch/test git repos go in `test-playground/` (gitignored). Build them there and **leave them** - the user opens them to test the TUIs by hand.
- **Never take a README screenshot or record a GIF by hand.** Every file in `readme-assets/` is rendered by VHS from `demo/` (`cargo build --release && cd demo && ./render.sh`), against six invented repos `demo/stage.sh` builds and deletes. A UI change means rerunning a tape; a new asset means a new tape or a new `Screenshot` line, never a terminal and a crop. Nothing real may reach a frame: no repo of the user's, no absolute home path, no rig directory name.
- **Each README section is an interactive tool and its plain twin, answered from the same fixture** (`iscan`/`search`/`scan`, `irepos`/`repos`, `ilog`/`trace`, `istatus`/`status`, `ibranch`/`tidy`, `itag`/`tag`), because that pairing is what sluuz *is*. The section opens on the tool's GIF, one tape per feature, since a GIF's first frame is what a README shows before it plays; the plain command's output is read rather than watched, so it is a still (`<feature>-plain.png`), and every one of those comes from `plain.tape`, whose own GIF is recorded into the stage and deleted with it. VHS does not redraw while hidden, so a `Screenshot` cannot be taken off-camera inside a feature tape. There is no single tour GIF: adding one would show every beat a second time at double the bytes. The only still of a tool is `ilog-diff.png`, a diff being something you read, taken by a `Screenshot` line inside the clip that already covers it.

## Invariants and gotchas
- **When editing TUI keys - plain = top pane, Ctrl = the pane below it.** `j/k`≡`↑/↓` and `h/l`≡`←/→` drive the top pane; `Ctrl-j/k`≡`Ctrl-↑/↓` move the pane below, which on a diff means scrolling, with `Ctrl-h/l`≡`Ctrl-←/→` panning. There are no paging keys: a held key speeds up instead, through the one `Accel` in `tui/input.rs` that every view asks how far a press goes, so a new view never hardcodes a step and `PgUp`/`PgDn`, which many keyboards lack, are not needed. `/` filters the top pane and `?` the one below, each shown on its own pane's title with the key that opened it, so a query can never look like it went to the other box. A scope slider is drawn as tabs on its pane's border (`scope_tabs` in `tui/widgets.rs`: every stop named, the picked one filled cyan like a picked button, `│` between, at most five with `‹`/`›` when more are hidden), never as the one word for the stop you are on. The footer row under the panes (`key_footer` in `tui/widgets.rs`) lists what a screen can *do* (`actions` in `app/ui.rs`), never how to move, with `:help` pinned to its right edge however narrow the window; `:` opens a command line there (`CommandLine`: an empty line runs `help`, `:q` quits), and `:help` opens a cyan reader (`Modal::reader`) with every key (`help`). The footer is also the 3-second status line. A pane border says what the pane is, how far through it you are, and `/ filter` or `? filter`, which is where the filter shows once typed. `r` reads the current level again from git, keeping the cursor on what it was on by name, since a refresh is exactly when positions shift. `Esc` = back, `Enter` = open/drill in (on a diff: the user's `git difftool`). Hint labels come from the `Y_MOVE`/`CTRL_Y_MOVE`/`X_MOVE`/`CTRL_X_MOVE` consts in `tui/input.rs` - never hand-write a key hint.
- **When parsing git output where leading whitespace is significant** (notably `git status --porcelain`, whose first column is a space for unstaged files), use `git_capture_raw`, not `git_capture`: the latter `.trim()`s, which ate the leading space of the first record and shifted the whole line ("Cargo.lock" → "argo.lock").
- **When running git against paths it reported** (`git status --porcelain`, `git show --name-status`), anchor at the repo root (`git rev-parse --show-toplevel`): git reports paths root-relative, so `diff`/`add`/`show -- <path>` from a subdirectory silently mis-resolves - istatus showed "Could not access '<path>'", ilog/ibranch a blank diff pane. Every view now resolves the root once and passes it down: **no view calls `set_current_dir`**, and every loader in `git/load.rs` takes the repo as its first argument, which is what lets `irepos` walk several repos in one session.
- **When a TUI talks to a remote** (`itag`'s `git ls-remote`): go through `unattended_git` in `git/load.rs`. A credential or passphrase prompt would be typed into a screen that is not reading it, and ssh asks on `/dev/tty` rather than stdin, so `GIT_TERMINAL_PROMPT=0` alone does not stop it: the ssh command gets `-o BatchMode=yes` appended, and a remote that wanted a prompt reads as unreachable.
- **When reading a remote's tags:** git keeps no copy of them by default, so `itag` asks with `ls-remote` unless the repo has `tag_rule` (`+refs/tags/*:refs/remote-tags/<remote>/*`, added by `t` with the user's yes), in which case git's own copy is drawn at once and refreshed with a tags-only `fetch --no-tags --prune`. Keep that copy outside `refs/remotes/`: under it every tag lists as a remote branch in `git branch -r` (and in `ibranch`), and a branch called `tags/x` lands on the same ref as a tag called `x`. Never cache the answer anywhere git does not maintain it - a copy only `itag` updates goes stale on the user's own `git push --tags`.
- **When a TUI shells out to an interactive program** (e.g. `git difftool`), you must suspend it: pop the kitty flags → `ratatui::restore()` → run → `ratatui::init()` → re-push. Check `diff.tool`/`merge.tool` *first*, so an unconfigured user gets a message instead of a torn-down screen. See `run_difftool` in `tui/difftool.rs`.
- **When handling `Esc`:** the kitty protocol we push (DISAMBIGUATE_ESCAPE_CODES) turns `Ctrl-[` into a distinct key instead of the ESC byte. `norm_esc()` in `tui/input.rs` folds it back - call it on every key event, or vim users lose `Ctrl-[`.
- **When a diff pane shows a hunk that starts mid-file, the highlighter needs the lines above it**: syntect enters a hunk with a clean state, so a closing `"""` reads as an opening one and stains every line under it. `prepare_diff` takes a `DiffContext` - one lazily-fetched blob per side - and primes itself at each `@@`; a new diff caller hands it one (`commit_diff_ctx` in `git/load.rs` for a commit, `blobs_for` in `istatus.rs` for the index/worktree pair) or its diffs go back to being stained.
- **When the diff view feels laggy:** highlight ONCE with `prepare_diff` (syntect is the expensive part), then `render_prepared` re-lays-out per scroll/pan. Never re-highlight on a keypress.
- **When deciding which branches are safe to delete** (`tidy`, and `d` in `ibranch`): use "upstream gone" (`%(upstream:track)` contains `[gone]`), never `git branch --merged` - merged-into-HEAD wrongly lists `main` and release branches that are still alive on the remote. Gone is only the sign a branch is finished, not proof its work reached the remote, so both then ask `load::landed` (or find no commit of its own): `tidy` offers only those, with `git branch -D` because `-d` refuses anything squash- or rebase-merged, and lists the rest apart.
- **When `d` deletes something** (`app/delete.rs`), which box it gets is decided by who loses what. The Yes/No gate (opens on No) is for what is finished or cheap to recreate: a branch whose upstream is gone, a tag no remote has (every tag, when there is no remote). A branch whose commits no remote has (`unique_commits`) still gets the plain gate when `landed` shows their changes are already in the remote's trunk (`merge-tree` of the branch into it leaves the trunk's tree unchanged), which is how a squash or rebase merge leaves a finished branch; counting commits alone cannot tell, since those merges give the same changes new ids, and a conflict reads as not landed so the check only errs towards asking. Every delete from this clone records the ref's old object (and a branch's upstream config, which `git branch -D` drops) so `u` can put it back exactly. The typed gate (`typed_popup`: Enter does nothing until the exact name is typed) is for what cannot be taken back and that others depend on or that exists nowhere else: a branch holding changes that have not landed, a branch or tag on the remote (`push_delete`, run after the frame that says so, like `s`), and a pushed tag, which goes on the remote *and* here since deleting it only here lasts until the next fetch. Everything else - `main`, `master` or the remote's default branch (`is_trunk`, here or on the remote, whatever state it is in), the checked-out branch, one still alive on its remote - is refused with a `Modal` saying why, never a silent no-op.
- **When reading a branch name to feed `git branch -d`:** take `%(refname)` and strip `refs/heads/`. `%(refname:short)` returns `heads/v1.2.3` when a tag shares the name, which `git branch -d` then rejects.
- **When adding a command, `slu --help` groups it by the `i` prefix.** The command list is rendered by `help_template` in `main.rs`, not by clap, which has no way to give one subcommand a different heading from another: a name starting with `i` goes in the interactive group and everything else in the plain one, which is the naming rule above read back rather than a second list kept beside it. Both halves are built from clap's own metadata, so nothing is written twice, and the `Cmd` enum is laid out in the two blocks it prints in so the source reads the way the help does. The one thing to keep in mind is that a *plain* command starting with `i` would be grouped wrong, which is another reason not to name one that way.
- **When adding a level to the drill** (`Repos` → `Branches` → `Commits` → `Diff`, with `Tags` standing where `Branches` would): it is ONE app in `src/app/`, not one per command. Add the `Level`, its scope slider, its `enter_*` loader, an arm in `app/keys.rs` and one in `app/ui.rs`. `irepos`/`ibranch`/`itag`/`ilog` are ~40-line commands that only pick the level to start at, and `Esc` quits at whichever level that was (`App::back`). `Tags` is only ever a start level, so `Level::back` takes the start to know that a tag's commits step back to it, and `request_commits` reads the same start to walk a tag's own range instead of `log_args` as a plain log.
- **When a level's bottom pane previews the next level down: never load it on the keypress.** A cursor move only sets `App::pending`; the load is asked for once the input queue drains (`event::poll(ZERO)` in `App::event_loop`), so a held `j` scrolls at the speed of the terminal instead of one `git log` per row. The load itself is a thread streaming rows in batches (`git/load.rs`, `stream_rows`) that the drawing loop drains a frame at a time, and a request the cursor has moved past is cancelled mid-walk through the shared `Feed::latest` counter - on a repo whose git calls cost 300ms (a Windows drive over WSL's 9p bridge is the case that found this), doing any of it synchronously is what made `ibranch` unusable. Loading the level *below* the preview still happens only on `Enter`.
- **When behavior doesn't match the code you just wrote:** the debug binary is stale. `cargo clean -p sluuz`, then rebuild. The usual cause is a `cargo publish` (dry run included): its verify build shares the fingerprint of the normal one and leaves it pointing at the copy in `target/package/`, so cargo reports `Fresh` however much `src/` changes.
- `syntect` is pinned to `default-features=false` + `default-fancy` - the pure-Rust regex backend, so there's no C/oniguruma and it builds on Windows. Don't "fix" the feature flags.
- `slu completions` delegates to git's own completion (that's the only way branch names complete). git's completion is **lazy-loaded**, and completing `slu` never trips that loader - so the emitted script force-loads it.
- `slu self update` on Windows renames the running `slu.exe` aside first: Windows cannot overwrite a running binary.
- VS Code's integrated terminal cannot distinguish `Ctrl-J` from `Enter` on any OS (not just Windows). The fix is a user `keybindings.json` remap to `Ctrl-Down` - see README Troubleshooting; there is no code-side fix.

## Build / lint / test
- `cargo build --release`, binary at `target/release/slu`.
- Run the debug binary directly as `./target/debug/slu <cmd>` (there is no dev.sh).
- The TUIs have no tests: everything covered here is pure logic.
- `cd demo && ./render.sh` re-renders every README asset (needs `vhs`, `ttyd` and `ffmpeg` on PATH); `./render.sh <tape>` does one of `plain` / `sleuth` / `repos` / `history` / `status` / `tags` / `branches` against a freshly staged world. `./stage.sh up` then `./stage.sh shell` drops you in that world by hand, which is also the fastest way to try a TUI against interesting fixtures; `./stage.sh down` deletes it.

## Overview
`sluuz` is a Rust CLI on crates.io that is a **git superset**: the binary is `slu` (a 3-letter stand-in for `git`). Anything git understands is passed straight through to real git; on top, `slu` adds cross-repo management, history/secret search, a prettier log, and interactive TUIs. Crate `sluuz`, binary `slu`, AGPL-3.0-only.
Layout:
- `src/main.rs` - the clap `Cmd` enum, `passthrough()`, and the `--help` command list, which is rendered here rather than by clap.
- `src/git.rs` - repo discovery, `git_capture{,_raw}`/`git_run`, `RepoStatus`, `SEP`, and `git/load.rs` for the queries the interactive views run (they sit here, not under `tui/`, because reading git is not terminal work and a plain command may need the same query).
- `src/history.rs` - the pickaxe shared by `search`, `scan` and `iscan`.
- `src/app/` - **the drill**: one `App` with a `Level` stack (`Repos` → `Branches` → `Commits` → `Diff`; the file list is the preview pane at `Commits`, not a level of its own, so three `Enter`s take you from a repo list to a diff), split into `repos`/`branches`/`tags`/`commits`/`diff` state, `keys.rs` for input and `ui.rs` for rendering. `irepos`, `ibranch`, `itag` and `ilog` are four entry points into it.
- `src/tui/` - primitives with no view knowledge: `input` (key predicates + hint labels), `widgets`, `highlight` (syntect), `difftool`, and terminal setup in `mod.rs`.
- `src/commands/` - one file per command. `iscan` and `istatus` stay standalone (a query bar and a staging area have no place in a nav stack) but wear the same shape: a state struct, `on_key`, `draw`.
- `demo/` - the rig that renders `readme-assets/`: `stage.sh` (the invented world), six feature tapes (`sleuth`/`repos`/`history`/`status`/`tags`/`branches`) and `plain.tape` for the plain commands' stills, `render.sh` (stage once, run the tapes in order, tear down). Every tape is 960x600 = 100x30, one size for all of them: `Set Height` mid-tape resizes the canvas but not the pty, so a tape cannot change frame size, and the frame is sized for the longest scrolling report since a TUI fills whatever it is given. The width is what decides whether the pictures can be read: a README fits them to about 758px, so 100 columns puts a character at ~7.6px where 148 put it at ~5.1px and the text came out too small to read. Going narrower still is the side-by-side diff's call - at 100 columns it has ~50 a side, which is where the fixture's longest lines begin to need panning. Excluded from the published crate.
